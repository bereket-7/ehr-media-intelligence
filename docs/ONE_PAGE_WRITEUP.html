1Overview & Architecture
Local-First Modular Service Architecture

The platform ingests unstructured synthetic EHR media records (JSON, CSV, TXT), cleans and normalizes fields into a validated canonical schema, maps them into valid HL7 FHIR R4 resources, generates structured evidence-grounded AI clinical summaries with deterministic offline fallback, and indexes records into vector storage for semantic natural language retrieval.

[Raw Files: JSON/CSV/TXT] → IngestionService (Clean • Dedup • Quarantine) → SqliteRepository (Patients • MediaRecords • Bundles • Cache) → SearchService (all-MiniLM-L6-v2) → FastAPI / SPA UI
2Ingestion & FHIR R4 Mapping
  • Multi-Format Parsers: Ingests JSON arrays, CSV spreadsheets, and plain text with automatic boundary validation and field-level audit trails.
  • Cleaning & Normalization: Dates standardized to ISO 8601 (YYYY-MM-DD); administrative genders normalized; raw clinical texts preserved.
  • Identity & Conflict Quarantine: Missing MRNs receive deterministic keys (pat_synth_...); MRNs with conflicting names are quarantined (CONFLICT_QUARANTINED) to prevent data corruption.
  • Duplicate Suppression: MD5 content fingerprinting suppresses duplicate documents while updating audit logs.
  • FHIR R4 Resources: Mapped via fhir.resources: Demographics → Patient; Notes/Imaging → DocumentReference; Labs → DiagnosticReport; assembled into per-patient collection Bundle with validated references.
3AI Summarization & Retrieval
  • Structured Clinical Summary: Extensible provider interface supporting OpenAI gpt-4o-mini with strict Pydantic v2 schemas: Chief Concern, Diagnoses, Key Findings, Abnormalities, and Data Quality Issues.
  • Length & Safety Enforcement: Narratives constrained strictly under 200 words with mandatory AI advisory disclaimer.
  • Deterministic Offline Fallback: Operates 100% offline without API keys, extracting factual clinical records safely without hallucination.
  • Content-Hash Cache: SQLite cache keyed by MD5(patient_key + records_hash + model + prompt_v) avoids redundant API calls.
  • Semantic Vector Search: Embeddings generated via all-MiniLM-L6-v2; persists in ChromaDB / EmbeddedVectorStore; retrieves top-K with cosine similarity ≥ 0 and filters by type, date, patient.
4Key Engineering Trade-offs
  • Local-First vs. Cloud Databases: Chose SQLite and embedded vector stores over cloud infrastructure (Postgres/Milvus) for zero-configuration, reproducible local evaluation.
  • Deterministic Fallback vs. LLM-Only: Built an offline rule-based extraction engine so the platform never fails when API keys or network access are absent.
  • Vanilla JS vs. Heavy SPA Frameworks: Built the dashboard with native ES6+ and Tailwind CDN, eliminating build step complexities, Node runtime drift, and compilation overhead.
  • Conservative Identity Resolution: Never merges patients based on fuzzy name matching; strictly isolates records when identifiers conflict.

6Limitations & Future Engineering Directions
Terminology Standards: Currently preserves raw clinical texts and codes. Future production iterations should integrate external terminology servers for LOINC, SNOMED CT, and RxNorm ontology mapping.
Enterprise Security & Scale: Transition from assessment prototype to production EHR integration requires SMART-on-FHIR OAuth2 authentication, distributed vector indexing (e.g. Qdrant), and HIPAA-compliant audit trails.
